# Beacon wire and assistance contract, v1

The shared implementation is `packages/protocol/src/index.ts`. The native BLE module transports its UTF-8 JSON as base64 and performs byte fragmentation below this layer. A complete application packet must fit 16,384 UTF-8 bytes. No production transport fallback exists in this package; automated tests use an explicit in-memory transport and repository.

## Identity and signatures

A local identity contains a 32-byte Ed25519 private seed, 32-byte public key, and node ID equal to SHA-256 of the public key, all lowercase hex. `createIdentity(randomBytes)` requires an injected cryptographically secure random source. The application must persist private material in secure storage. Node IDs never depend on Bluetooth addresses or native session identifiers.

An immutable `Envelope` contains `version`, `id`, `type`, `origin`, `publicKey`, `nonce`, `destination`, `createdAt`, `expiresAt`, `hopLimit`, `requestId`, `revision`, `payload`, and `signature`. All timestamps use integer Unix milliseconds. Destination is either a node ID or the literal `community`. A request ID is generated by `createRequestId`: the first 128 bits of the requester's node fingerprint followed by 128 random bits. The reducer rejects roots whose fingerprint does not match their signer; another device cannot claim an existing request by sending its own SOS with that ID.

Canonical encoding recursively sorts object keys lexicographically, preserves array order, uses JavaScript JSON string/number serialization, and omits undefined object properties. Runtime schemas forbid unknown fields and nonfinite numbers. The message ID is SHA-256 of the canonical body without ID/signature. The signature is Ed25519 over the canonical body including ID and excluding signature. `verifyEnvelope` and the flat `EnvelopeSchema` verify structure, identity binding, ID hash, TTL bounds, and strict Ed25519 signatures. History verification intentionally does not reject old authenticated messages. `decodePacket` also rejects expired or excessively future-dated live traffic.

Mutable routing metadata is outside the signature: `{ envelope, hops }`. Origin storage starts at zero hops; each transmission sends `stored.hops + 1`. The immutable hop limit and expiry are authenticated. A recipient may accept the final permitted hop but cannot forward it further. An untrusted relay can lie about hop count: this is bounded cooperative flooding, not a cryptographic proof of the entire path.

The included `tests/protocol/wire-vector.json` is a complete deterministic interoperability vector with an explicitly public synthetic private key. Tests also use the RFC 8032 empty-message signature vector. Never use this fixture key for real identities.

These are self-generated identities, not verified names or qualifications. Signatures authenticate message ownership, not whether a person is trustworthy. Mesh payloads are plaintext; there is no claim of end-to-end encryption, community enrollment, or protection against colluding Sybil devices. No sensitive information belongs in BLE advertisement data. The first direct signed inventory is a versioned identity announcement, not challenge-response authentication of the physical radio session.

## Message types and authority

| Type | Payload | Authority/effect |
| --- | --- | --- |
| `sos` | category, note, displayName, location | Requester creates revision 0 community request |
| `receipt` | messageId | Explicit participant endpoint confirms persistence of a referenced SOS; never automatic for relays |
| `seen` | messageId | Participant's explicit human acknowledgment, separate from persistence |
| `offer` | displayName, note | Volunteer offers assistance to requester |
| `accept` | offerId, helperId, assignmentId | Only requester; positive increasing revision; directed to selected helper |
| `assignment_receipt` | messageId, assignmentId | Selected helper confirms receiving the authenticated current acceptance at its exact revision |
| `cancel` | reason | Only requester; increasing revision, community tombstone |
| `complete` | note | Only requester; increasing revision, community tombstone |
| `inventory` | up to 64 message IDs | Direct signed control; never persisted or relayed |
| `missing` | up to 64 message IDs | Direct signed request for retained messages; never persisted or relayed |

Categories are trapped, injured, stranded, and other. Location is a timestamped report with source `device`, `manual_pin`, `manual_description`, or `unavailable`. Device/manual-pin reports require both coordinates. Manual descriptions require a nonblank description. Unavailable reports assert neither coordinates nor accuracy. Accuracy, building, floor, room, and descriptive text are optional. No radio-derived physical location is inferred.

`deriveRequests(envelopes)` is pure and re-verifies signatures. It reconstructs state from all available authenticated history, resolves dependencies regardless of arrival order, and applies requester revisions in increasing order. Only valid offers may be accepted. Same-revision conflicts are deterministically ordered by event time then ID; the requester should never produce such forks. Cancellation and completion are terminal and cannot be reopened by replay, including a later purported acceptance. UI must continue showing partitions as potentially missing later information. Assignment receipts are accepted only from the selected helper and only for the exact acceptance message, request, assignment, and revision.

Transport and human state remain separate. A relay's successful SQLite write or BLE transmission never creates an SOS recipient receipt. When a user intentionally opens/participates in a received request, the app may call `router.acknowledge(sosMessageId)`: this device then declares itself an intended endpoint and signs a persistence receipt. Reading/acknowledging as a human is represented separately by `seen`. The selected helper's assignment receipt is automatic only after SOS, offer, and acceptance dependencies establish a valid assignment. It is generated even if those dependencies arrive out of order. Receipts themselves are never acknowledged, and repeated endpoint acknowledgment reuses the existing receipt.

## Router and persistence integration

Construct `MeshRouter` with identity, `repository`, `transport.send(peerId, wire)`, `clock`, secure `randomBytes`, and UI/error callbacks. Transport send resolves on native write completion; it must not await downstream application processing. `publish` durably saves before attempting forwarding. The mobile service sets `awaitForwarding: false` with an error callback, so publish and receive return after persistence instead of waiting for slow native sends. Background flush requests are coalesced, and independent peer links flush concurrently within the peer and send bounds. Callers that omit this option retain the await-forwarding behavior. `receive` validates and durably deduplicates before applying receipt behavior or forwarding. `connect` registers a native session, exchanges a signed bounded inventory, requests missing records, and flushes traffic. `disconnect` releases all per-session state. Foreground callers should periodically call `flush` to retry failed writes and drain backlogs beyond one batch. No JavaScript timer or background execution guarantee is embedded here.

Repository contract:

```ts
interface MessageRepository {
  listMessages(): Promise<StoredMessage[]>;
  getMessage(id: string): Promise<StoredMessage | undefined>;
  saveMessage(envelope: Envelope, hops: number, receivedAt: number): Promise<boolean>;
  listForwarded(peerId: string): Promise<string[]>;
  markForwarded(peerId: string, messageId: string): Promise<void>;
}
// StoredMessage = { envelope, hops, receivedAt }
```

`saveMessage` returns false only for an already known stable ID. It must transactionally save the envelope, deduplication entry, derived/event records, and upload outbox as appropriate, and enforce capacity inside the same transaction. Storage failure/capacity exhaustion must throw and must not appear as safely queued. An adapter may improve a duplicate's stored hop count when a shorter route arrives while keeping its application effect deduplicated. Forwarding records represent completed native sends, never delivery evidence. They should be recorded separately from envelope identity and original TTL. Successful sends invoke the change callback. Supply `onError` to show retryable send failures; absent it, send failure is thrown.

Persistent forwarding history supports UI/audit. The router's per-session sent set is reset on reconnect, so persistence loss or disconnect does not permanently suppress delivery. Fresh missing requests can override this set once per record per minute. Replayed control IDs and duplicate IDs within a control do not cause additional transmissions. Unknown inventory IDs are never retained in the suppression set; all retained per-session ID sets are capped. Returned receipts are ordinary bounded messages and can follow any later contact; the original route need not remain connected. This is at-least-once transport with deduplicated application effects.

Retain terminal tombstones and deduplication history for at least the longest accepted message TTL plus clock tolerance (seven days plus five minutes), and do not silently evict active records to make capacity. The SQLite adapter owns retention and pruning. For cancellation/completion publish with `ttlMs: LIMITS.maxTtlMs`; ordinary SOS defaults to six hours. Expiry limits propagation, while retained history remains available for replay. Expired records must not be revived by a new relay timestamp.

## Concrete bounds

| Limit | Value | Reason |
| --- | --- | --- |
| Complete wire packet | 16 KiB | Matches native reassembly maximum |
| Note length | 280 characters | Short assistance reports |
| Direct inventory/missing list | 64 IDs | Bounded reconnect work |
| Hop limit | 8 | Practical demonstration flooding radius |
| Default TTL | 6 hours | Useful outage window |
| Maximum TTL | 7 days | Terminal propagation and finite retention |
| Future clock tolerance | 5 minutes | Bounded clock skew; not clock synchronization |
| Durable messages | 2,000 | SQLite transaction-enforced prototype cap |
| Active peer sessions | 16 | Bounded per-session state |
| Sends per peer per flush | 64 | Bounded foreground work |
| Incoming packets per session | 240/minute | Simple packet processing throttle |
| Outgoing data packets per session | 240/minute | Limits forced-retransmission amplification |
| Concurrent receive operations / data sends | 8 each per session | Bounds in-flight work without an unbounded promise queue |
| Seen/suppressed IDs and requested record cooldowns | 2,000 each per session | Bounded rolling retention |
| Control replay IDs | 2,048 per session | Retained until signed expiry; reject new controls at capacity |
| Control TTL | 60 seconds | Limits live control replay window |

Acknowledgments and authoritative updates receive priority, then SOS, then remaining traffic. One quarter of forwarding slots select the oldest pending message across priorities, preventing low-priority starvation under acknowledgment traffic. Repeated flushes drain remaining pages. Signed control requests are rate limited like other incoming packets. Their request ID must be all zeroes, revision zero, and hop count zero. Self-announcements and changed identity announcements within a session are rejected. Duplicate connect notifications preserve the session’s existing throttles. Concurrent endpoint acknowledgments share one operation; assignment reconciliation runs serially and repeats when concurrent arrivals change history. Multiple native sessions claiming the same remote identity remain independent bounded links: the announcement is not a challenge-response proof, so using it to evict another link would introduce an identity-replay denial of service. These links must not be presented as a count of unique people. This is resource protection for a prototype, not comprehensive denial-of-service defense.

## Verification

Run `node --import tsx --test tests/protocol/*.test.ts tests/adversarial/*.test.ts`. Tests cover Ed25519/vector compatibility; malformed and oversized input; expiry, future clocks and hops; connected A–B–C forwarding and return receipt; disconnected store-carry-forward with relay restart; repeated acknowledgments without loops; wrong-request acknowledgments; forged authority; conflicting offers; cancellation surviving stale replay; out-of-order assignment dependencies; unavailable location; failed-write retries; and forwarding fairness.

These are automated protocol tests. Native fragmentation/reassembly and physical Android/iPhone interoperability are separate workstreams. Passing this suite does not validate BLE range, actual hardware delivery, reliable background operation, or rescue outcomes.
