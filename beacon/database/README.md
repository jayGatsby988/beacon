# Beacon event storage

Run `npm --workspace @beacon/api run migrate` with a **server-side** `DATABASE_URL` and `DB_SSL=require` for Tiger Cloud. Migrations require a role permitted to create Timescale objects; the runtime role should be a separate, scoped role. No cloud resources are provisioned by this repository. Running the API locally does not prove Tiger Data connectivity.

`event_dedupe` is an ordinary PostgreSQL table with a globally unique event ID and unique `(device_id, sequence)`. Its insert and the hypertable event insert commit together. Same ID/content is a retry; same ID with changed fields or reused device sequence is rejected. Concurrent conflicts block until the owning transaction finishes. An interrupted transaction never leaves a dedupe-only record. Do not reset a device's persistent sequence while retaining the same identity.

`events` partitions by the reported occurrence time. Late upload is allowed, including expired but valid signed messages. API bounds timestamps to 2000–2100 and rejects future observations beyond five minutes. `ingested_at` records server arrival independently. There is intentionally no automatic retention/deletion policy: organizers must decide retention with participants before real use; deleting dedupe rows prematurely re-enables old retries.

The hourly continuous aggregate groups observed event kinds by incident. It counts phone observations, not unique SOS requests. A seven-day rolling policy runs every five minutes. Every accepted event also upserts its full UTC hour into `aggregate_refresh_queue` atomically. The server worker processes up to 48 hours per minute, calls `refresh_continuous_aggregate` with exact hour boundaries, and deletes only the revision it refreshed. A concurrent late arrival increments the revision and leaves work queued. Failures remain queued across server restarts. An operator can run `npm --workspace @beacon/api run refresh`. Summary counts and signed request statistics query raw records immediately; hourly aggregate output is explicitly labeled pending until refresh finishes. Historical buckets outside the rolling window are therefore eventually refreshed as well.

Use a database snapshot/backup and verify restoration before any real deployment. Test integration against a disposable Timescale database only: `BEACON_TEST_DATABASE_URL=... npm --workspace @beacon/api test` (destructive schema creation within a unique test schema, cleaned up afterward; see test source). The isolated local PostgreSQL 18.6 / TimescaleDB 2.30.2 run passed this integration test, the complete workspace suite (50 passed, zero skipped), and real HTTP ingestion/replay/summary checks including 30-day-late refresh.
